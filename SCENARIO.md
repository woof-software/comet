# Scenarios

Scenarios are high-level property and ad-hoc tests for the Comet protocol. To run and check scenarios:

`npx hardhat scenario`

## Running Scenarios

You can run scenarios against a given base as:

`npx hardhat scenario --bases development,linea,mainnet`

You can run scenarios from a specific file (or files matching a glob pattern) with `--glob`:

`npx hardhat scenario --glob 'scenario/AllowBySigScenario.ts'`

`npx hardhat scenario --glob 'scenario/AllowBySigScenario.ts' --bases development`

The default is `scenario/**.ts` (all scenario files). The pattern is passed to [fast-glob](https://github.com/mrmlnc/fast-glob); quote it in the shell so paths and braces are not expanded by bash. Combine with `--bases` to limit which deployment environments are used.

You can run spider persistently first if you wish:

`npx hardhat scenario --spider`

Note: if you want to speed up, probably better to first:

`npx hardhat deploy --simulate --overwrite`

You can write the JSON report somewhere other than the default `scenario-results.json`:

`npx hardhat scenario --bases mainnet --output results/mainnet.json`

## Running Scenarios in Parallel (multistream)

`scenario` works through its bases one after another. `scenario:multistream` splits them into groups and runs each group as its own `yarn scenario` child process, in parallel:

`yarn scenario:multistream`

`yarn scenario:multistream --bases mainnet,mainnet-weth,base-usdc,base-weth`

By default there is one stream per **network**, and the bases on that network run sequentially inside it. That grouping is deliberate: bases sharing a network also share a bridge token's entry in the contract cache, and keeping them in one stream keeps two processes from writing that file at once.

Before launching anything, multistream runs `yarn build` and then warms the spider cache — mainnet first, since every L2 scenario depends on the shared `auxiliaryBase`, then the remaining bases together in one call.

Each stream writes two files:

- `logs/<group>.log` — that stream's full output
- `results/<group>.json` — that stream's JSON report

Once every stream has finished, the per-stream reports are merged into `scenario-results.json` in the repo root and a per-stream pass/fail summary is printed. The task exits non-zero if any stream exited non-zero, or if the merged report contains failures. Both `logs/` and `results/` are gitignored.

Locally, each stream's output is echoed to your terminal as it runs. Under `CI=true` it isn't, because the per-stream logs are uploaded as artifacts and shown separately.

### Sharding per base

`--per-base` gives every base its own stream instead of grouping by network:

`yarn scenario:multistream --bases base-usdc,base-weth --per-base`

This is faster, but for networks with more than one base (arbitrum, base, optimism, polygon, linea, ronin) it knowingly gives up the protection described above — those bases share a bridge token's cache entry and will now write it concurrently. It is a speed-for-correctness trade, not a safe default, and the task prints a warning when you pass it.

### Spidering on its own

`scenario:spider` runs spider for a set of bases without running any scenarios:

`yarn hardhat scenario:spider --bases mainnet,base-usdc`

Bases are spidered concurrently and independently: one base failing — a flaky RPC, an explorer returning 500s — no longer abandons the others. The task fails only after every base has had its chance, and names each one that failed.

### In CI

The **Run Scenarios** workflow takes a `multistream` boolean input:

- `false` (the default) — one job per base, ~29 jobs, each running `yarn scenario`.
- `true` — one job per network, ~11 jobs, each running `scenario:multistream --per-base` across that network's bases. A follow-up `display-scenario-logs` job then surfaces each base's full log as its own job page.

The matrix is generated by `scripts/multistream/generateCiMatrix.ts` from `hardhat.config.ts`'s `scenario.bases`, so adding a market to that config is enough — there is no second list to keep in sync.

## Adding New Scenarios

To add a new scenario, add to `scenario/`, e.g.

**scenario/NewToken.ts**

```ts
import { scenario } from './context/CometContext';
import { expect } from 'chai';
import { BigNumber } from 'ethers';
import { World } from '../plugins/scenario';

scenario('Comet#allow > allows a user to authorize a manager', { upgrade: true }, async ({ comet, actors }) => {
  const { albert, betty } = actors;

  await albert.allow(betty, true);

  expect(await comet.isAllowed(albert.address, betty.address)).to.be.true;
});
```

For more information, see the Scenarios Hardhat plugin.

## Constraints

### Modern Constraint

**requirements**: `{ upgrade: true }`

This constraint is to indicate that all deployments must use the most recent version of the Comet contract. For instance, say your scenario uses a feature that's not available on certain test-nets (or mainnet), then you would otherwise not be able to run the scenario on those networks. But if you include `{upgrade: true}` in your constraint requirements, the scenario will deploy a new Comet instance and upgrade the proxy to that before running the scenario. Note: currently this simply uses the `deploy.ts` script for deployment.
